## Experiment 1: does date-partitioned Parquet for Silver help the reconciliation engine?

**Question.** The incremental engine evaluates a fixed ~6k items per day, but its queries still scan Silver. Would partitioning Silver by date reduce that scan cost?

**Method.** For each scale the same synthetic Silver history (deterministic, SQL-generated, daily volume fixed at 3,000 orders so the *history* grows) is stored two ways: **baseline** = DuckDB tables (what the pipeline uses); **partitioned** = hive-partitioned Parquet (one folder per date) exposed to the **unchanged** engine through views. The same next-day batch is applied to both; the real incremental reconciliation is run on both; the final reconciliation states must be identical (checked). 1x is the 30-day / 3,000-orders-a-day benchmark (~86k items). Rows scanned come from DuckDB's profiler (compute phase only, profiling on); timings are separate runs without profiling (median of the repetitions shown). Peak RSS is the sampled peak of the process tree (50 ms sampling, so a lower bound).

### Conclusion (from the numbers above)

* **Partitioning did not help; it made the unchanged engine slower at every scale tested** (1.4x to 7.1x slower incremental compute, 1x to 50x), while scanning several times more rows. The layouts produced identical reconciliation state, so this is purely a cost difference.
* **Why (interpretation, consistent with the micro-benchmark):** the engine looks records up by key (`txn_id IN (...)`), not by date, so partition pruning never applies; each of ~60 statements re-reads the view, and reading many small Parquet files costs more than scanning one DuckDB table.
* **A date bound does help when a query can carry one:** in the micro-benchmark a date-bounded lookup is faster than an unbounded one in both layouts, but the *table* with a date bound (min/max zone maps on a date-ordered table) is still faster than partitioned Parquet with a partition bound, so partitioning is not what delivers the benefit.
* **Ingestion is the only place Parquet wins**, and it is not the bottleneck: it saves fractions of a second and does not produce the change log the engine depends on.
* **Recommendation:** do not adopt partitioned Parquet for Silver. If scan cost matters at larger history, the experiment to run next is a date-bounded engine on the existing table layout (queries with a `created_at >=` bound for recent scope, unbounded fallback for late arrivals). That has **not** been implemented or measured.

**Reading:** incremental evaluates far fewer items, but wall-clock gain over an in-process full rebuild is modest (1.6x at 90 days) and end-to-end daily runtime is dominated by dbt (~9 s of a ~13 s day). Experiment 1 shows why incremental *compute* still grows with history: statements scan whole Silver tables.
